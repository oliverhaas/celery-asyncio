## Methodology notes

<!-- keep:methodology -->
* **Every config is measured for the same 60 s, not for the same number of
  tasks.** A driver thread keeps ~4000 tasks outstanding so the pool never
  starves, and completions are counted with `DBSIZE` on the result backend at
  the two ends of the window. Earlier revisions drained a fixed 10 000 tasks,
  which gave the fastest configs 7 s of measurement and the slowest 21 minutes;
  the interesting cells got the worst error bars.
* The first 10 s after the worker reports ready are discarded. That covers a
  prefork pool still forking children and every pool filling its prefetch
  buffer.
* Each result carries a `harness` version. `render_results.py` drops anything
  below the current one instead of mixing it into a table, and separately drops
  any run whose window length differs from the rest. Mixing measurement methods
  in one table is how three earlier revisions of this document went wrong.
* Memory is reported as **PSS** as well as RSS. Summing RSS over a prefork tree
  counts every copy-on-write page once per child, which roughly doubles the
  reported footprint of a 100-process pool. Both figures are read from a single
  `/proc/<pid>/smaps_rollup` snapshot, so PSS can never exceed its own RSS.
* `mean_cpu` is summed across cores. On the 4-core taskset 100 % is one core
  saturated and 400 % is all four.
* Worker subprocesses run in their own session. Check `mingle: all alone` in
  the worker logs before trusting numbers: orphaned workers from an earlier run
  steal tasks and silently tank throughput. This bit us once, so the
  kill-everything pre-flight is now part of the routine.
* Single runs on a workstation, not a dedicated bench machine. TPS reproduces
  within a few percent across reruns; `mean_cpu` is noisier.

### Observations

<!-- keep:obs-mixed -->
**1.3x over the best upstream config, 1.5x over the best prefork.**
`aio-async-l4c25-314t` sustains 1380.3 TPS against 1062.9 for
`classic-threads100-314t` and 930.8 for `classic-prefork100-314`. It does so on
319 MB PSS against 2854 MB, so the throughput lead comes with an 8.9x smaller
footprint.

**Free-threading is what moves the needle, and only for single-process pools.**
The asyncio pool goes 470.1 to 1380.3 TPS from 3.14 to 3.14t (2.94x) and
upstream's thread pool goes 443.0 to 1062.9 (2.40x). Prefork goes *backwards*,
930.8 to 868.8, because it already had its parallelism from processes and now
just pays the free-threaded build's single-thread penalty.

**Seven configs sit in a band at ~150 TPS, and they are all 4-slot configs.**
`aio-sync-s4` on both builds, `classic-prefork4` on both, and
`aio-mixed-l2c50-s2-314t` land between 149.3 and 153.8 TPS. Four execution
slots against a 40 % I/O workload is four slots whatever the pool underneath.
Only the configs that actually `await` break out. **The win is the async task,
not the async pool**: running celery-asyncio with sync task bodies buys nothing
over prefork here.

**The GIL build is where the asyncio pool is merely competitive.** At 470.1 TPS
it beats upstream's thread pool (443.0) but loses to prefork (930.8), which is
the expected shape: one process cannot outrun four when the work has a 30 % CPU
component and no free-threading to spread it.

### Observations

This is the profile where prefork should be untouchable: pure CPU, no `await`
to hide behind. It is, on a GIL build, and it is not on 3.14t.

**On 3.14, only prefork uses more than one core.** Every single-process config,
ours and upstream's threads pool alike, sits at 101 % CPU and 55.1 to 55.9 TPS.
The spread across six such configs is 0.8 TPS, which is the GIL being the only
thing that matters. Prefork reaches 208.2 to 214.4 TPS at ~400 %.

**On 3.14t the single-process pools catch prefork exactly.**
`aio-async-l4c25-314t` does 205.5 TPS at 399 % against `classic-prefork25-314`
at 214.4, and every 3.14t config with 25 or more slots lands in a 195 to 206
TPS band regardless of pool. Four cores are four cores. What separates them is
memory: 122 MB PSS for the asyncio pool, 728 MB for prefork25 (6.0x) and
2563 MB for prefork100 (21x). **This is the result the project exists for:
multicore CPU throughput without paying per-child memory.**

**`classic-threads4-314t` does not scale and we do not yet know why.** It
manages 62.9 TPS at 123 % CPU while `aio-sync-s4-314t`, also four threads on
the same interpreter, does 202.1 at 393 %. The io-only profile shows the same
config hitting exactly 8.0 TPS, which is four concurrent 0.5 s sleeps, so the
pool really is running four tasks at once and the shortfall is CPU parallelism
rather than a slot count. Upstream's thread pool at 25 and 100 threads scales
fine (198.6 and 198.7 TPS), so it is specific to the small pool. Open question,
not yet diagnosed.

### Observations

<!-- keep:obs-io-only -->
**This profile is slot arithmetic, and every config now hits its ceiling.**
With `io_seconds=0.5`, a config with N slots can do at most 2N tasks per
second, and essentially every row is exactly on that line: 100 slots gives
~200 TPS, 25 gives 50.0, 4 gives 8.0, 1 gives 2.0. Nothing here is
throughput-limited by its pool, so **throughput is not the story: memory is.**

**At identical throughput, prefork costs 33x the memory.** All six 100-slot
configs land at 199.6 to 200.0 TPS. `aio-async-l4c25-314` holds 80 MB PSS,
`classic-threads100-314` 82 MB, and `classic-prefork100-314` 2678 MB. On RSS,
which is what an orchestrator actually schedules against, the gap is 88 MB
against 5095 MB, or 58x.

**That is the whole cost result.** Idealised Fargate cost for those same rows
is $0.01 per million tasks for the asyncio pool and $0.05 for prefork100, a 5x
difference at the same 200 TPS, driven by 441 against 25 470 MB-seconds per
thousand tasks. Prefork is paying to hold a hundred interpreter copies resident
while all hundred of them are blocked in `sleep`.

**`aio-mixed-l2c50-s2` caps at 47.3 TPS** despite having 102 slots, because
part of the workload routes to its 2 sync threads and that half sets the pace.
A mixed layout is only as concurrent as its least concurrent half.

### Observations

<!-- keep:obs-memory -->
**Read the PSS column, not RSS, for prefork.** RSS counts every copy-on-write
page once per child, so `classic-prefork100-314t` reports 6396 MB resident on a
machine with 31 GB while the pool's actual cost to the host is 2855 MB. For
single-process configs the two agree within 10 MB, because there is nothing to
share.

**PSS per slot is the number that separates the pool types, and it is flat for
prefork.** Every prefork config costs 25 to 39 MB per slot no matter how many
slots it has: 38.4 MB at 4 slots, 28.1 at 25, 25.4 at 100. That is one Python
heap per slot and it does not amortise. Single-process pools go the other way,
from 9 to 25 MB per slot at 4 slots down to 0.4 to 1.2 MB at 100, because the
interpreter is paid for once and a slot is only a coroutine or a thread stack.

**The free-threaded build costs a fixed 40 to 90 MB more per process.** Compare
any `-314` row with its `-314t` twin: `aio-async-l4c25` goes 40 to 122 MB PSS
on cpu-only, `classic-threads100` 46 to 107. It is a per-interpreter constant,
not per slot, so it is noise for a single-process pool and it is why
`classic-prefork100-314t` is the most expensive cell in the matrix.
<!-- /keep -->

## uvloop

`aio-async-l4c25` on the mixed workload, with and without `BENCH_UVLOOP=1`. This is the whole uvloop result; it is not carried through the other tables.

| python | selector loop TPS | uvloop TPS | delta |
| --- | ---: | ---: | ---: |
| 3.14 | 470.1 | 465.7 | -0.9 % |
| 3.14t | 1380.3 | 1467.8 | +6.3 % |

<!-- keep:obs-uvloop -->
**Real, but under the bar.** On the mixed workload uvloop is worth +6.2 % on
the free-threaded build and nothing at all on the GIL build (-0.9 %). The
free-threaded figure is not noise: over four runs each, uvloop averages 1433.6
TPS against 1349.5 and the two sample ranges do not overlap
([1391, 1468] against [1261, 1386], rank test p ~ 0.03). It is a genuine 6 %
that costs a compiled dependency, which is a judgement call rather than a
recommendation. On cpu-only it is slightly negative (-5.4 % to +0.4 %), and on
io-only both configs sit on the 200 TPS slot ceiling so the comparison says
nothing.

**It helps only where the loop is on the critical path.** The GIL build runs
this config at 104.9 % CPU, meaning one saturated core: the bottleneck is the
GIL, so making the event loop cheaper buys nothing and uvloop measures as noise.
The free-threaded build runs it at 374 % across four loop threads, where loop
overhead is both on the critical path and paid four times over, and there the
same change converts into throughput. This is the opposite of what the socket
micro-benchmark alone would predict, which is why the matrix number is the one
to trust.

**The budget explains the size.** A task here costs 2.2 ms to 3.4 ms of CPU,
while uvloop saves roughly 11 us per socket round-trip on the GIL build (24.0 us
against 12.8 us, `socket_micro.py` against `fakeapi.py` on idle cores). The
transport uvloop replaces really is exercised: kombu-asyncio drives the broker
through `redis.asyncio`, so every task does asyncio socket I/O for its fetch,
ack and result write. A task would need on the order of 30 socket round-trips
before that per-round-trip saving alone reached +10 %.

**If you do have socket-heavy tasks on the GIL build, most of uvloop's
advantage there is not the event loop.** `_SelectorSocketTransport.max_size` is
256 KiB and the stdlib transport allocates that buffer per `recv`, which glibc
malloc serves past its 128 KiB mmap threshold. `PYTHONMALLOC=mimalloc` alone
takes the same socket benchmark from 24.0 us to 13.7 us per round-trip, most of
what uvloop buys, with no dependency. The free-threaded build already defaults
to mimalloc.

## Summary

<!-- keep:summary -->
Against upstream celery 5.6.3 on the same hardware and broker, each config
measured over the same 60 s window:

| workload | best celery-asyncio | best upstream celery | TPS | memory |
| --- | --- | --- | ---: | ---: |
| mixed | 1380.3 TPS / 319 MB (`aio-async-l4c25-314t`) | 1062.9 TPS / 530 MB (`classic-threads100-314t`) | 1.30 x | 1.7 x |
| cpu-only | 205.5 TPS / 122 MB (`aio-async-l4c25-314t`) | 214.4 TPS / 703 MB (`classic-prefork25-314`) | 0.96 x | 5.8 x |
| io-only | 199.6 TPS / 80 MB (`aio-async-l4c25-314`) | 200.0 TPS / 2678 MB (`classic-prefork100-314`) | 1.00 x | 33 x |

Memory is peak PSS. Upstream's best is chosen by throughput, which on io-only
picks prefork; note that `classic-threads100-314` also reaches 199.6 TPS on
82 MB, so **the memory gap is against prefork specifically, not against
upstream in general.**

Read together, three conditions decide whether this package is worth adopting,
and all three have to hold:

1. **The task bodies must be `async def`.** Sync bodies on the asyncio pool
   perform exactly like prefork on every profile, because four slots is four
   slots. Seven configs prove this by landing within 5 TPS of each other on
   mixed.
2. **You must want the concurrency in one process.** At matched slot counts the
   throughput difference is between nil and 1.3x. What changes by an order of
   magnitude is what those slots cost: 0.4 to 1.2 MB PSS per slot against
   prefork's flat 25 to 39 MB, at any pool size.
3. **For CPU-bound work, free-threading is required to break even.** On a GIL
   build the single-process pool tops out at one core and prefork wins
   outright, 214.4 against 55.7 TPS. On 3.14t it matches prefork (205.5 against
   214.4) on a sixth of the memory.

Cost follows memory, not speed. Idealised Fargate cost is nearly flat across
the mixed table ($0.03 to $0.05 per million) because it bills only consumed CPU
and RSS, and the bench app is bare-bones. The separation appears once a
realistic worker footprint is modelled, since prefork pays it per child: at
800 MB per process the asyncio pool is 2.0x cheaper and at 5 GB it is 4.9x, and
it is ahead at every point on the crossover table including 100 MB.

## History

<!-- keep:history -->
### Fixed-duration measurement (August 2026)

Every number above is from a 60 s measurement window. Earlier revisions of this
document drained a fixed 10 000 tasks per config and reported wall-clock, which
had two problems. The fast configs were measured for about 7 s, so the headline
cells had the worst statistics in the matrix. And the slow configs were
measured for up to 21 minutes, which made a full sweep take hours and pushed
several cells past the 1800 s cap so they had no row at all.

Comparing methods rather than builds also inflated the headlines. The old
summary claimed **9.4x** on mixed and **24.8x** on io-only. Both compared the
best asyncio config against `classic-prefork4`, a 4-slot config, while the
asyncio config had 101 slots. Measured against upstream configs with matching
slot counts, mixed is **1.3x** and io-only is **1.0x** on throughput with the
real difference (33x) in memory. The project's case is memory and CPU
efficiency at a given concurrency, not raw throughput.

Two harness bugs were fixed on the way to this run:

- **PSS could exceed RSS.** `memory_info().rss` and `memory_full_info().pss`
  are separate `/proc` reads, and mem_heavy tasks allocating 8 MiB buffers
  moved between them; one mixed run reported 377 MB PSS against 273 MB RSS.
  Both figures now come from one `smaps_rollup` snapshot. Zero violations
  across all 78 runs.
- **`peak_cpu` over-read for prefork**, up to 1164 % on a 4-core taskset,
  because the measured span included the fork ramp. The warmup window removed
  it.

### Sampler fix (May 2026)

The sampler used to recreate `psutil.Process` objects for each child on every
iteration. `cpu_percent(interval=None)` computes the delta against the
*previous call on the same Process object*, so brand-new objects returned 0 %
every cycle. For single-process configs the parent was primed once and readings
were accurate; **for multi-process configs every child read 0 % on its first
sample and prefork CPU was severely undercounted** (mean_cpu ~16 % when four
cores were running). The fix caches Process objects by PID and primes new
children on first sight.

### Strand bug fixed (May 2026)

The May 14 mixed-workload table reported 21 to 48 stranded tasks per aio config
(0.07 to 0.16 %). Fixed in kombu-asyncio
[#4](https://github.com/oliverhaas/kombu-asyncio/pull/4) (long-lived consumer
iterations) plus restore-on-cancel for cold paths.
