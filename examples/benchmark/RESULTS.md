## Methodology notes

<!-- keep:methodology -->
* **Every config is measured for the same 60 s, not for the same number of
  tasks.** A driver thread keeps ~4000 tasks outstanding so the pool never
  starves, and completions are counted with `DBSIZE` on the result backend at
  the two ends of the window. Earlier revisions drained a fixed 10 000 tasks,
  which gave the fastest configs 7 s of measurement and the slowest 21 minutes;
  the interesting cells got the worst error bars.
* The first 10 s after the worker reports ready are discarded. That covers a
  prefork pool still forking children and every pool filling its prefetch
  buffer.
* Each result carries a `harness` version. `render_results.py` drops anything
  below the current one instead of mixing it into a table, and separately drops
  any run whose window length differs from the rest. Mixing measurement methods
  in one table is how three earlier revisions of this document went wrong.
* Memory is reported as **PSS** as well as RSS. Summing RSS over a prefork tree
  counts every copy-on-write page once per child, which roughly doubles the
  reported footprint of a 100-process pool. Both figures are read from a single
  `/proc/<pid>/smaps_rollup` snapshot, so PSS can never exceed its own RSS.
* `mean_cpu` is summed across cores. On the 4-core taskset 100 % is one core
  saturated and 400 % is all four.
* Worker subprocesses run in their own session. Check `mingle: all alone` in
  the worker logs before trusting numbers: orphaned workers from an earlier run
  steal tasks and silently tank throughput. This bit us once, so the
  kill-everything pre-flight is now part of the routine.
* Single runs on a workstation, not a dedicated bench machine. TPS reproduces
  within a few percent across reruns; `mean_cpu` is noisier.

### Observations

<!-- keep:obs-mixed -->
**1.5x over the best upstream config, 1.7x over the best prefork.**
`aio-async-l4c25-314t` sustains 1584.9 TPS against 1062.9 for
`classic-threads100-314t` and 930.8 for `classic-prefork100-314`. It does so on
258 MB PSS against 2854 MB, so the throughput lead comes with an 11x smaller
footprint.

**Free-threading is what moves the needle, and only for single-process pools.**
The asyncio pool goes 485.9 to 1584.9 TPS from 3.14 to 3.14t (3.26x) and
upstream's thread pool goes 443.0 to 1062.9 (2.40x). Prefork goes *backwards*,
930.8 to 868.8, because it already had its parallelism from processes and now
just pays the free-threaded build's single-thread penalty.

**Six configs sit in a band at ~150 TPS, and all of them run like 4-slot
configs.** `aio-sync-s4` and `classic-prefork4` on both builds land between
150.7 and 153.8 TPS: four execution slots against a 40 % I/O workload is four
slots whatever the pool underneath. `aio-mixed-l2c50-s2` joins them on both
builds at 149.3 and 150.3 despite its 100 async slots, because half its tasks
go to two sync threads and those set the pace (see the io-only observations).
Only the configs that actually `await` break out. **The win is the async task,
not the async pool**: running celery-asyncio with sync task bodies buys nothing
over prefork here.

**The GIL build is where the asyncio pool is merely competitive.** At 485.9 TPS
it beats upstream's thread pool (443.0) but loses to prefork (930.8), which is
the expected shape: one process cannot outrun four when the work has a 30 % CPU
component and no free-threading to spread it.

This is the profile where prefork should be untouchable: pure CPU, no `await`
to hide behind. It is, on a GIL build, and it is not on 3.14t.

**On 3.14, only prefork uses more than one core.** Every single-process config,

manages 62.9 TPS at 123 % CPU while `aio-sync-s4-314t`, also four threads on

config hitting exactly 8.0 TPS, which is four concurrent 0.5 s sleeps, so the

rather than a slot count. Upstream's thread pool at 25 and 100 threads scales
fine (198.6 and 198.7 TPS), so it is specific to the small pool. Open question,
not yet diagnosed.

### Observations

<!-- keep:obs-io-only -->
**This profile is slot arithmetic, and every config now hits its ceiling.**
With `io_seconds=0.5`, a config with N slots can do at most 2N tasks per
second, and essentially every row is exactly on that line: 100 slots gives
~200 TPS, 25 gives 50.0, 4 gives 8.0, 1 gives 2.0. Nothing here is
throughput-limited by its pool, so **throughput is not the story: memory is.**

**At identical throughput, prefork costs 60x the memory.** All six 100-slot
configs land at 198.3 to 200.0 TPS. `aio-async-l4c25-314` holds 45 MB PSS,
`classic-threads100-314` 82 MB, and `classic-prefork100-314` 2678 MB. On RSS,
which is what an orchestrator actually schedules against, the gap is 54 MB
against 5095 MB, or 94x.

**That is the whole cost result.** Idealised Fargate cost for those same rows
is $0.005 per million tasks for the asyncio pool and $0.049 for prefork100, a
10x difference at the same 200 TPS, driven by 273 against 25 470 MB-seconds per
thousand tasks. Prefork is paying to hold a hundred interpreter copies resident
while all hundred of them are blocked in `sleep`.

**`aio-mixed-l2c50-s2` runs at 8.0 TPS**, a 4-slot pool's rate, despite having
102 slots. Half the workload routes to its 2 sync threads, which complete 4.0
TPS between them. Sync tasks waiting for a thread hold the prefetch window, so
the async half gets a new task only when a sync one starts and frees a slot,
and the total is twice the sync half's 4.0. A mixed layout is only as
concurrent as its least concurrent half.

### Observations

<!-- keep:obs-memory -->
**Read the PSS column, not RSS, for prefork.** RSS counts every copy-on-write
page once per child, so `classic-prefork100-314t` reports 6396 MB resident on a
machine with 31 GB while the pool's actual cost to the host is 2855 MB. For
single-process configs the two agree within 10 MB, because there is nothing to
share.

**PSS per slot is the number that separates the pool types, and it is flat for
prefork.** Every prefork config costs 25 to 39 MB per slot no matter how many
slots it has: 38.4 MB at 4 slots, 28.1 at 25, 25.4 at 100. That is one Python
heap per slot and it does not amortise. Single-process pools go the other way,
from 10 to 16 MB per slot at 4 slots down to 0.4 to 2.2 MB at 100, because the
interpreter is paid for once and a slot is only a coroutine or a thread stack.

**The free-threaded build's extra memory grows with threads, not slots.**
Compare any `-314` row with its `-314t` twin on cpu-only or io-only. Upstream's
thread pool pays 16 MB more PSS at 4 threads, 41 to 46 at 25 and 61 to 135 at
100. The asyncio pool pays 21 to 32 MB at every size from 4 slots to 102,
because it runs the same handful of threads however many tasks it holds.
Prefork pays about 12 MB of RSS per process, mostly in shared pages, so its PSS
barely moves, but 101 processes of it put `classic-prefork100-314t` 1.2 GB of
RSS above its GIL twin.

<!-- keep:obs-uvloop -->
**Real on the free-threaded build, and small.** The table is one run of each.
Over four runs each, uvloop averages 1641.4 TPS against 1607.0 on the
free-threaded build, +2.1 %, and the two sample ranges do not overlap
([1627.7, 1663.0] against [1584.9, 1620.6], rank test p ~ 0.03). On the GIL
build the table's +2.9 % does not hold up: four runs each average 474.9 against
496.0, and the ranges overlap ([443.1, 500.2] against [485.9, 504.5], p ~ 0.2).
August measured +6.2 % on the free-threaded build. The likely reason it shrank
is that a task now makes fewer socket round-trips, since the worker sends the
acks, result writes and events of one loop pass together. Two percent does not
pay for a compiled dependency. On cpu-only the deltas run from -1.5 % to
+1.1 %, and on io-only every config sits on its slot ceiling, so neither
comparison says anything.

**It helps only where the loop is on the critical path.** The GIL build runs
this config at 103 to 104 % CPU, meaning one saturated core: the bottleneck is
the GIL, so making the event loop cheaper buys nothing. The free-threaded build
runs it at 385 to 393 % across four loop threads, where loop overhead is both
on the critical path and paid four times over, and there the same change
converts into throughput. This is the opposite of what the socket
micro-benchmark alone would predict, which is why the matrix number is the one
to trust.

**The budget explains the size.** A task here costs 2.1 ms to 2.4 ms of CPU,
while uvloop saves roughly 11 us per socket round-trip on the GIL build (24.0 us
against 12.8 us, `socket_micro.py` against `fakeapi.py` on idle cores). The
transport uvloop replaces really is exercised: celery-asyncio's kombu drives the
broker through `redis.asyncio`, so every task does asyncio socket I/O for its
fetch, ack and result write. A task would need on the order of 20 socket
round-trips before that per-round-trip saving alone reached +10 %.

**If you do have socket-heavy tasks on the GIL build, most of uvloop's
advantage there is not the event loop.** `_SelectorSocketTransport.max_size` is
256 KiB and the stdlib transport allocates that buffer per `recv`, which glibc
malloc serves past its 128 KiB mmap threshold. `PYTHONMALLOC=mimalloc` alone
takes the same socket benchmark from 24.0 us to 13.7 us per round-trip, most of
what uvloop buys, with no dependency. The free-threaded build already defaults
to mimalloc.

## Where the per-task cost goes

<!-- keep:obs-profile -->
The framework table once left taskiq about 14% cheaper per task than
celery-asyncio (3% now), and a guess about why. The guess was wrong. What
follows is how it was measured and what the answer turned out to be, because two
of the three methods gave confident wrong answers first.

**A sampling profiler is not enough.** `bench_profile.py` samples every thread
and buckets by package, which is sound. Its leaf attribution is not. It put 6.3%
of on-CPU time in `_weakrefset._remove`, from the `WeakSet` that
`celery/worker/state.py` keeps of reserved and active requests. A microbenchmark
priced those callbacks at 0.47 us per task, and swapping both sets for plain
sets measured 1482.9 TPS against a 1503.7 baseline, which is nothing. It made
the same kind of claim about `json/decoder.py:__init__`, roughly 21 us per task
against a microbenchmark's 0.13 us. Read that profiler's package split; do not
read its top frames.

**A ceiling first, then the gap.** `bench_ceiling.py` runs the same task bodies
in the same pool shape with no framework at all, and costs 2.033 core-ms per
task. celery-asyncio cost 2.51 and taskiq 2.18, so the thing to explain was
about 480 us per task against taskiq's 150 us.

**Counting beats guessing.** `bench_counts.py` uses `sys.monitoring` for exact
Python call counts: celery-asyncio 595 per task, taskiq 830. celery-asyncio
executes *fewer* Python calls than the framework beating it, which kills the
protocol-overhead story outright. What differed was Redis traffic. Redis'
`INFO commandstats` charged celery-asyncio two transport round-trips per task,
one `EVALSHA` to consume and one to acknowledge, against taskiq's one: its
`XREADGROUP` fetches 100 messages at a time, so only the `XACK` is per-task.
Adding one deliberate round-trip to the task body priced one at about 70 core-us
and 3.2% of throughput.

**What the deterministic profiler said.** `bench_dprof.py` counts and times
every Python call through `sys.monitoring`, so there is no sampling bias, and it
calibrates its own per-event overhead. Self-time on a single-loop worker, scaled
onto the 2545 core-us the same configuration costs unprofiled:

| bucket | core-us/task | share |
| --- | ---: | ---: |
| task body and bench counter | 1484 | 58.3 % |
| redis-py client | 427 | 16.8 % |
| stdlib asyncio, socket and loop | 405 | 15.9 % |
| celery | 156 | 6.1 % |
| kombu | 73 | 2.9 % |

celery and kombu's own Python work is 229 us, 9% of the budget. The Redis client
stack is 832 us at 3.04 commands per task, so the cost tracks the *number of
commands*, and celery-asyncio was issuing three where taskiq issued two.

**So the fix was batching, not trimming.** `prefetch_count` was never
implemented on this transport: `celery/worker/consumer/tasks.py` defined
`set_prefetch_count` as `pass`, nothing called `QoS.update()`, and
`valkey_redis.py` had no reference to it. On AMQP prefetch works because
RabbitMQ pushes; on Redis kombu pulls, one message per round-trip. The consume
Lua script now takes a maximum message count, returns a batch, and the channel
hands them out from a local buffer.

| `worker_prefetch_multiplier` | median TPS | core-ms/task | EVALSHA/task | Redis CPU/task |
| --- | ---: | ---: | ---: | ---: |
| 0, one message per call | 1502 | 2.51 | 2.00 | 31.0 us |
| 4 | 1587 | 2.42 | | |
| 16 | 1583 | 2.39 | 1.01 | 19.5 us |

Two round-trips per task became one, which is what taskiq's stream broker does,
and the published row moved from 1504 to 1655 TPS and from 394 to 431 tasks per
core-second; it stands at 1682 and 435 now. No separation between multiplier 4
and 16: the first batch captures essentially all of it.

**One wrong turn, since put right.** The batch size started as
`prefetch_count - len(self._delivered)`, an AMQP-style cap on unacknowledged
messages. Logging the sizes showed 12070 calls asking for one message against
248 asking for a hundred: unacknowledged messages filled to the cap under load
and then the batching stopped. The count was changed to bound only the local
buffer, which let a worker claim messages however many it already held, until
eb78f66e3 made it an AMQP-style cap again. This time the batches held. A 3 s
`MONITOR` sample in the middle of a fw-celery-aio window caught 174 consume
calls claiming 5022 messages: half the calls claimed three or fewer, but 91 % of
the messages came in calls of 50 or more. The acks of one loop pass go out in
one script call, 14.7 per call on average. Over a whole run that is 0.077
`EVALSHA` per task, against the 1.01 in the table.

**Left on the table.** redis-py 7.4's `observability/recorder.py` runs 27 times
per task here, and with telemetry disabled every one of them calls
`_get_or_create_collector()`, which walks the provider chain and returns `None`
without caching that answer. `celery/app/trace.py` builds `saferepr(R)` on every
successful task for a log line that `_does_info` discards at anything above INFO.
Neither has been A/B'd; both are small.

## Summary

<!-- keep:summary -->
Against upstream celery 5.6.3 on the same hardware and broker, each config
measured over the same 60 s window:

| workload | best celery-asyncio | best upstream celery | TPS | memory |
| --- | --- | --- | ---: | ---: |
| mixed | 1584.9 TPS / 258 MB (`aio-async-l4c25-314t`) | 1062.9 TPS / 530 MB (`classic-threads100-314t`) | 1.49 x | 2.1 x |
| cpu-only | 206.7 TPS / 71 MB (`aio-async-l4c25-314t`) | 214.4 TPS / 703 MB (`classic-prefork25-314`) | 0.96 x | 9.9 x |
| io-only | 199.0 TPS / 45 MB (`aio-async-l4c25-314`) | 200.0 TPS / 2678 MB (`classic-prefork100-314`) | 0.99 x | 60 x |

Memory is peak PSS. Upstream's best is chosen by throughput, which on io-only
picks prefork; note that `classic-threads100-314` also reaches 199.6 TPS on
82 MB, so **the large memory gap is against prefork specifically; against
upstream's thread pool it is 1.8x.**

A separate table measures four other Python task queues on the same workload;
the short version is that celery-asyncio's single free-threaded process needs
the least memory of the at-least-once rows for its throughput, only taskiq is
faster, and taskiq is about 3% cheaper per task.

Read together, three conditions decide whether this package is worth adopting,
and all three have to hold:

1. **The task bodies must be `async def`.** Sync bodies on the asyncio pool do
   no better than prefork on any profile, because four slots is four slots.
   Six configs prove this by landing within 5 TPS of each other on mixed.
2. **You must want the concurrency in one process.** At matched slot counts the
   throughput difference is between nil and 1.5x. What changes by an order of
   magnitude is what those slots cost: 0.4 to 0.7 MB PSS per slot against
   prefork's flat 25 to 39 MB, at any pool size.
3. **For CPU-bound work, free-threading is required to break even.** On a GIL
   build the single-process pool tops out at one core and prefork wins
   outright, 214.4 against 54.3 TPS. On 3.14t it matches prefork (206.7 against
   214.4) on a tenth of the memory.

Cost follows memory, not speed. Idealised Fargate cost is nearly flat across
the mixed table ($0.02 to $0.05 per million) because it bills only consumed CPU
and RSS, and the bench app is bare-bones. The separation appears once a
realistic worker footprint is modelled, since prefork pays it per child: at
800 MB per process the asyncio pool is 2.1x cheaper and at 5 GB it is 5.1x, and
it is ahead at every point on the crossover table including 100 MB.

## Known issues surfaced

<!-- keep:known-issues -->
**Zero stranded tasks across all 78 runs**, so the May strand fix (kombu-asyncio
[#4](https://github.com/oliverhaas/kombu-asyncio/pull/4)) holds up.

**All 78 cells produced a result.** Under fixed-duration measurement there is
nothing left to time out: a config that is too slow to drain 10 000 tasks now
simply reports a low TPS. The three cells that had no row in earlier revisions
(`classic-threads4-314` on mixed, `classic-prefork1` on io-only for both
builds) are present here at 51.6, 2.0 and 2.0 TPS.

**A sub-millisecond fanout wait went out as `XREAD BLOCK 0`.** The first
attempt at the current celery-asyncio rows logged `Connection to broker lost`
mid-window on a broker that was fine, and the reconnect redelivered tasks the
worker had already run, so some ran twice. The read for control commands and
events waits for whatever is left of the consumer loop's wait, converted to
milliseconds by truncation, and Redis reads `BLOCK 0` as no timeout at all, so
the read sat until the 15 s socket timeout gave up on the connection. It came
with 6.0.0a6 and is fixed in bf3d9f007, which every celery-asyncio row here
ran; every matrix row's worker log was checked for lost connections and for
tasks that ran twice.

**`classic-threads4-314t` scales to only 1.2 cores on cpu-only** while the same
four threads under `aio-sync-s4-314t` reach 4.0. See the cpu-only observations;
this is an open question, not a harness artifact, and it is upstream's pool
rather than ours.

`peak_cpu` used to over-read badly for prefork (1164 % against a 4-core
taskset) because the fixed-count runs included the fork ramp, where children
primed at different moments double-counted across a `cpu_percent` interval.
Measuring a steady-state window after warmup fixed it: prefork now peaks at 396
to 412 %, and `peak_cpu` is usable again.

**Do not run `ruff` over the repo while a matrix is in flight.** `fix = true`
rewrites files in place and `run_all.py` exec's a fresh `runner.py` per config.
One cell died with `[Errno 2] No such file or directory` on `runner.py` because
the two coincided, and the stale JSON left behind then ranked as the fastest
config in the mixed table until `render_results.py` learned to drop it.

### Fixed-duration measurement (August 2026)

Every number above is from a 60 s measurement window. Earlier revisions of this
document drained a fixed 10 000 tasks per config and reported wall-clock, which
had two problems. The fast configs were measured for about 7 s, so the headline
cells had the worst statistics in the matrix. And the slow configs were
measured for up to 21 minutes, which made a full sweep take hours and pushed
several cells past the 1800 s cap so they had no row at all.

Comparing methods rather than builds also inflated the headlines. The old
summary claimed **9.4x** on mixed and **24.8x** on io-only. Both compared the
best asyncio config against `classic-prefork4`, a 4-slot config, while the
asyncio config had 101 slots. Measured against upstream configs with matching
slot counts, mixed is **1.3x** and io-only is **1.0x** on throughput with the
real difference (33x) in memory. The project's case is memory and CPU
efficiency at a given concurrency, not raw throughput.

Two harness bugs were fixed on the way to this run:

- **PSS could exceed RSS.** `memory_info().rss` and `memory_full_info().pss`
  are separate `/proc` reads, and mem_heavy tasks allocating 8 MiB buffers
  moved between them; one mixed run reported 377 MB PSS against 273 MB RSS.
  Both figures now come from one `smaps_rollup` snapshot. Zero violations
  across all 78 runs.
- **`peak_cpu` over-read for prefork**, up to 1164 % on a 4-core taskset,
  because the measured span included the fork ramp. The warmup window removed
  it.

### Sampler fix (May 2026)

The sampler used to recreate `psutil.Process` objects for each child on every
iteration. `cpu_percent(interval=None)` computes the delta against the
*previous call on the same Process object*, so brand-new objects returned 0 %
every cycle. For single-process configs the parent was primed once and readings
were accurate; **for multi-process configs every child read 0 % on its first
sample and prefork CPU was severely undercounted** (mean_cpu ~16 % when four
cores were running). The fix caches Process objects by PID and primes new
children on first sight.

### Strand bug fixed (May 2026)

The May 14 mixed-workload table reported 21 to 48 stranded tasks per aio config
(0.07 to 0.16 %). Fixed in kombu-asyncio
[#4](https://github.com/oliverhaas/kombu-asyncio/pull/4) (long-lived consumer
iterations) plus restore-on-cancel for cold paths.
