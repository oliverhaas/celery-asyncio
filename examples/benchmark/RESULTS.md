## Methodology notes

<!-- keep:methodology -->
* Each row is a single run on a laptop, not a dedicated bench machine.
  **Wall and TPS are stable across reruns (±5 %); `mean_cpu` is noisier**
  because the psutil sampler depends on which child processes exist at
  sample time.
* Worker subprocesses run in their own session. Always check
  `mingle: all alone` in every worker log before trusting numbers —
  orphaned workers from previous bench runs steal tasks and silently
  tank throughput. This bug bit us once; the kill-everything pre-flight
  check is now part of the routine.
* `mean_cpu` is summed across CPU cores. On the 4-core taskset, 100 %
  ≈ one core saturated; 400 % ≈ all four cores saturated.

### Observations

<!-- keep:obs-mixed -->
**9.4× on wall-clock.** `aio-async-l4c25-uvloop-314t` finishes in 7.1 s
(1414.6 TPS); the best upstream config, `classic-prefork4-314`, takes 66.4 s
(150.6 TPS).

**Thirteen configs land within 1.5 s of each other at ~150 TPS.** That band
holds `classic-prefork4`, `aio-sync-s4` and `aio-mixed-l2c50-s2` on both
builds, with and without uvloop. They all run the blocking task, so all of
them are capped by 4 execution slots against a 40 % I/O workload; the pool
implementation underneath makes no measurable difference. Only the configs
that actually `await` (the `aio-async-l4c25` group, 100 in-flight slots)
break out of it. **The win is the async task, not the async pool**: running
celery-asyncio with sync task bodies buys nothing over prefork here.

**Free-threading rescues the thread pool.** `classic-threads4-314` never
finished: 6782/10000 at the 1800 s cap, under 3.8 TPS. The same config on
3.14t does 52.4 TPS. Upstream's `threads` pool is unusable on a GIL build for
this workload, which is why that row is absent above.

**uvloop earns its keep mainly under free-threading.** On 3.14 it is worth
45 % on the async config (458.7 vs 316.7 TPS); on 3.14t, 147 % (1414.6 vs
572.9). Elsewhere it is noise.

### Observations

<!-- keep:obs-cpu-only -->
This profile is the one where prefork should be untouchable: pure CPU, no
`await` to hide behind. It is, on a GIL build.

**On 3.14, only prefork uses more than one core.** Every single-process
config, ours and upstream's threads pool alike, sits at 101 % CPU and 52 to
55 TPS. `classic-prefork4-314` reaches 209.0 TPS at 400 %. Four processes,
four cores, exactly as expected.

**On 3.14t, the asyncio pool matches it in one process.**
`aio-async-l4c25-uvloop-314t` does 201.3 TPS at 393 %, within 4 % of
prefork4's 209.0, holding 104 MB peak RSS against 253 MB. Every 3.14t aio
config lands in the 191 to 201 TPS band. This is the result the project
exists for: multicore CPU throughput without paying per-child memory.

**Upstream's thread pool does not get there.** `classic-threads4-314t`
manages 83.1 TPS at 163 % CPU while `aio-sync-s4-314t`, also 4 threads on the
same interpreter, does 196.0 at 386 %. Same primitive, 2.4× apart, so the gap
is in how the pool dispatches rather than in free-threading itself.

**Caveat on `peak CPU` for prefork.** `classic-prefork4-314` reports 1164 %
peak against a 4-core taskset, which is impossible. Peak is a single sample,
and children primed at different moments briefly double-count across a
`cpu_percent` interval. `mean_cpu` (400 %) is the trustworthy figure; treat
`peak_cpu` for multi-process configs as an upper bound only.

### Observations

<!-- keep:obs-io-only -->
**25×, and the table splits cleanly in two.** The four `aio-async-l4c25`
configs finish in 50 to 61 s at 165 to 198 TPS. Every other config in the
matrix lands on 1252 s and 8.0 TPS, within a second of each other.

8.0 TPS is not a measurement, it is arithmetic: 10 000 tasks × 0.5 s over 4
concurrent slots is 1250 s. Four sync threads, four prefork children and
upstream's four pool threads are the same number. `aio-mixed-l2c50-s2` joins
them because half its workload routes to the 2 sync threads, and 5 000 × 0.5
over 2 is also 1250 s: the sync half sets the wall-clock and the 100 async
slots idle out the run.

**`classic-prefork1` could not finish.** 10 000 × 0.5 s serial is 5000 s, so
both builds hit the 1800 s cap and have no row.

**Idle billing is the real cost story.** The 8.0 TPS configs run at 1 % mean
CPU for 21 minutes: they are paying for wall-clock in which nothing computes.
`classic-prefork4-314t` costs $0.07 per million tasks against $0.01 for
`aio-async-l4c25-uvloop-314`, a 7× difference driven almost entirely by
holding 315 MB resident while blocked in `sleep`.

## Summary

<!-- keep:summary -->
Against upstream celery 5.6.3 on the same hardware, same broker and the same
10 000 task workloads:

| workload | best celery-asyncio | best upstream celery | ratio |
| --- | --- | --- | ---: |
| mixed | 1414.6 TPS (`aio-async-l4c25-uvloop-314t`) | 150.6 TPS (`classic-prefork4-314`) | 9.4 × |
| cpu-only | 201.3 TPS (`aio-async-l4c25-uvloop-314t`) | 209.0 TPS (`classic-prefork4-314`) | 0.96 × |
| io-only | 198.3 TPS (`aio-async-l4c25-uvloop-314`) | 8.0 TPS (`classic-prefork4-314`) | 24.8 × |

Read together, three conditions decide whether this package is worth
adopting, and all three have to hold:

1. **The task bodies must be `async def`.** Sync bodies on the asyncio pool
   perform exactly like prefork on every profile, because 4 slots is 4 slots.
2. **The work must actually wait on something.** The advantage is 25× when
   tasks are pure I/O, 9× on a 40 % I/O mix, and nil on pure CPU.
3. **For CPU-bound work, free-threading is required to break even.** On a GIL
   build the single-process pool tops out at one core and prefork wins on
   throughput; on 3.14t it matches prefork at 40 % of the memory.

Cost follows memory, not speed. Idealised Fargate cost is nearly flat across
the mixed table ($0.02 to $0.06 per million) because it bills only consumed
CPU and RSS. The separation shows up once a realistic worker footprint is
modelled: prefork pays it per child, so at 800 MB per process `aio` is 1.9×
cheaper and at 5 GB it is 3.0× cheaper, and it wins at every point on the
crossover table including 100 MB.

## History

<!-- keep:history -->
### Sampler fix (May 2026)

The sampler used to recreate `psutil.Process` objects for each child on
every iteration. `cpu_percent(interval=None)` computes the delta against
the *previous call on the same Process object*, so brand-new objects
returned 0 % every cycle. For single-process configs (aio, threads) the
parent process was primed once and the readings were accurate; **for
multi-process configs (prefork) every child read 0 % on its first
sample and the pool's CPU usage was severely undercounted** (mean_cpu
~16 % when 4 cores were actually running). The fix caches Process
objects by PID across iterations and primes new children on first
sight. The numbers below are the post-fix re-run.

What changed materially:

- `classic-prefork4-314` mixed `mean_cpu`: 20 % → **66 %**
- `classic-prefork4-314` cpu-only `mean_cpu`: 18 % → **389 %**
- `classic-prefork1-314` mixed `mean_cpu`: 6 % → **19 %**
- Idealised $/task for prefork rose ~3× — **prefork is no longer the
  dominant cost winner on mixed**; it now ties with aio configs at
  ~$0.05/M ideal Fargate.

### Strand bug fixed (May 2026)

The May 14 mixed-workload table reported 21–48 stranded tasks per aio
config (0.07–0.16 %). Fixed in kombu-asyncio
[#4](https://github.com/oliverhaas/kombu-asyncio/pull/4) (long-lived
consumer iterations) plus restore-on-cancel for cold paths.

**Result: `n_stranded = 0` on all 54 runs of this matrix.**
